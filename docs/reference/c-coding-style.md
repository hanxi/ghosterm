# C 语言编码规范

适用于项目自有 C 源码、头文件、C 实现片段（`.inc`）、JNI 和终端原生适配代码。
目标是让控制流、状态变化和资源归属容易阅读。架构、安全与验收规则仍以
[AGENTS.md](../../AGENTS.md) 为准；本文不新增或替代合并闸门。

## 自动排版

唯一排版配置为根目录 [`.clang-format`](../../.clang-format)，使用 **clang-format 19.1.7**。
固定补丁版本，避免不同开发环境反复改写同一文件。升级版本应单独评审配置与输出差异。
配置选项依据 [LLVM 19 官方格式选项文档](https://releases.llvm.org/19.1.0/tools/clang/docs/ClangFormatStyleOptions.html)。

| 项目 | 规则 |
| --- | --- |
| 缩进 | 4 个空格，不使用 Tab；续行基础缩进 4 个空格 |
| 行宽 | 100 列；不可拆分字符串、URL 等允许超长，不为排版改变字符串内容 |
| 花括号 | 左括号跟随声明或控制语句，右括号独占一行；`else` 跟随右括号 |
| 控制流 | `if/else/for/while/do` 即使只有一条语句也使用花括号 |
| 短语句 | 函数、条件、循环、枚举不压缩到单行；一行一条语句 |
| 指针 | `const char *name`、`gt_ssh_t **out`，星号靠变量 |
| 换行 | 参数放得下时保留一行；需要拆行时逐个参数换行并对齐 |
| 空行 | 函数之间一行；函数内按校验、计算、提交、清理等逻辑阶段分段 |
| include | 保留既有顺序和分组，不自动排序 |
| 注释 | 保留文字与人工换行，不自动重排段落 |

花括号内首尾不额外留空行；`else`、`else if` 和 `do/while` 的连接处不插空行。
紧密相关的声明、操作和错误检查放在一起，不逐条隔开。注释紧贴被说明的代码，
逻辑分段需要的空行放在注释之前。

`Language: Cpp` 是 clang-format 对 C/C++ 共用解析器的配置名称，`Standard: c++11`
也是该工具的解析选项，不改变工程的 **C11 + POSIX** 编译要求。
自动加花括号不能理解所有宏及条件编译边界，写回后仍须审查 diff 并编译验证。
不要用格式化工具重排宏来替代人工检查。

## 命名与表达式

- 函数、变量、参数和字段用 `snake_case`；类型沿用 `gt_*_t`，公开函数用 `gt_`，
  内部跨文件函数沿用 `gt__`，宏与枚举常量用大写下划线。文件内函数优先 `static`。
- 名称表达领域含义：`connector`、`deadline_ms`、`bytes_written`、`entry_count`。
  循环索引可用 `i/j`，短作用域且含义明确时可用 `fd/rc`；避免贯穿函数的 `a/c/e/p`。
- 布尔值用 `is_`、`has_`、`can_` 或含义明确的动词；单位写进名称或接口注释。
- 一条声明定义一个变量；指针、长度、容量的命名相互对应。变量靠近首次使用处声明。
- 避免在条件里赋值、嵌套三元表达式和逗号表达式；三元只用于无副作用的简单选择。
  `for` 的初始化与递增部分可保留惯用写法。
- 复杂条件提取有业务含义的局部变量或小函数，不按列宽机械拆出无含义的函数。
- 不为了遵守命名规范更改已有公共 ABI 或用户可见协议；命名重构单独提交。

## 函数与控制流

一个函数负责一个能清楚命名的操作。优先用提前返回处理非法输入和失败路径，
让正常路径按执行顺序阅读；出现三层以上嵌套或难以一屏理解时评估拆分，
不设可被机械拆函数规避的硬行数指标。

有资源需要统一释放时使用 `goto cleanup` 或含义明确的清理标签，按获取的逆序释放。
同一资源不要散落多个容易失配的清理分支。不能为了减少缩进改变取消、超时、
未知结果、连接代次或所有权转移的原有语义。

```c
gt_status_t gt_example_open(const gt_example_options_t *options, gt_example_t **out) {
    if (out != NULL) {
        *out = NULL;
    }
    if (options == NULL || out == NULL) {
        return GT_ERR_INVALID_ARG;
    }

    gt_example_t *example = calloc(1, sizeof(*example));
    if (example == NULL) {
        return GT_ERR_IO;
    }

    gt_status_t status = example_initialize(example, options);
    if (status != GT_OK) {
        example_destroy(example);
        return status;
    }

    *out = example;
    return GT_OK;
}
```

示例仅说明排版与所有权转移方式，不引入新 API 或改变既有错误码契约。

## 类型、内存与错误

- 长度、容量、索引用 `size_t`；ABI 和协议字段按契约使用固定宽度类型。
  有符号/无符号转换与窄化转换前检查范围，不以强制转换隐藏告警。
- 分配和偏移计算先检查加法、乘法溢出；使用 `sizeof(*pointer)`。
  缓冲区必须同时明确容量、有效长度和是否 NUL 结尾。
- 每个资源明确 owned/borrowed、释放函数、线程归属及转移时机。借用的 fd/指针不得释放，
  输出句柄按接口契约在失败时清空；失败后保留部分结果的接口必须明确说明。
- 检查分配、系统调用、锁和库调用的返回值；确实忽略结果时注明原因。
  系统错误需要跨清理步骤使用时立即保存 `errno`。
- 不将未知、拒绝、取消、失败合并成一个布尔值。缺能力显式返回
  `GT_ERR_UNSUPPORTED`；不使用断言代替生产输入校验。
- 不记录私钥、凭据或明文秘密；敏感临时内存沿用工程已有的安全清零机制。
  不以普通 `memset` 替代防优化擦除。

## 文件、头文件与注释

源文件依次放必要的特性宏、头文件、局部类型/常量、私有辅助函数和对外实现。
特性宏必须位于受其影响的系统头之前。人工新增 include 时区分项目头与系统头，
但保留有依赖意义的顺序；格式化不得排序。

公开头保持可独立 C11 编译、include guard 和必要的 C++ 链接保护；
子头不反向包含 `ghosterm.h`，平台绑定仍只从聚合头进入。
函数声明应说明输入限制、输出状态、所有权、线程/阻塞行为、取消与失败副作用。
只对真正的宏或编译期需求使用宏；多语句宏沿用 `do { ... } while (0)`，避免参数重复求值。

注释解释理由、边界和不变量，不翻译每条代码。复杂协议解析、状态机、清理与并发处
标明读者必须知道的约束。测试代码同样遵守可读性要求，不能把设置、动作、断言压在一行。
确有必要保留人工布局时，局部使用 `clang-format off/on` 并写明理由，不整文件关闭。

## 工具与使用

[scripts/format-c.py](../../scripts/format-c.py) 要求 Python 3.9+，不自动安装工具。
可用 `CLANG_FORMAT` 指定 **19.1.7** 可执行文件的路径；默认查找
`clang-format-19`，再查找 `clang-format`，版本不匹配直接报错。

从任意工作目录运行脚本均可；路径参数始终相对于仓库根目录。

```bash
# 仅列出范围，不调用 clang-format，也不需要安装它
python3 scripts/format-c.py --list

# 默认只检查；有差异退出 1，参数/工具错误退出 2
python3 scripts/format-c.py
python3 scripts/format-c.py --check core/src/ssh core/include

# 明确授权写回时才使用；当前制定规范阶段不要执行
python3 scripts/format-c.py --write core/src/ssh/authenticator.c
```

范围只包括 Git 已跟踪（含新暂存）的自有 `.c/.h/.inc`：`core/terminal/`、
各平台目录、`cli/`，以及 `scripts/lib/`、`scripts/probes/`。未跟踪文件需先暂存才会进入范围。
排除 `vendor/`、构建/生成目录、夹具和符号链接；不存在的已跟踪文件跳过。
`package-validator-code.inc`、`sdk-code.inc`、`sdk-identity.h`、`wire-schema.inc`
由生成器及摘要检查维护，即使位于源码目录也显式排除；需要调整其排版时应修改生成器。
不接收仓库外路径。检查与写回采用同一范围，不修改 Git 暂存区。
新生成目录出现时须同步脚本排除规则，不能仅靠 `.gitignore` 保护已跟踪文件。

## 渐进采用

项目自有 C 文件统一按上述工具排版。独立的
[C Format 工作流](../../.github/workflows/c-format.yml) 在 push main、PR 或手动触发时
安装固定版本并执行全范围 `--check`，不自动写回，不以路径过滤跳过检查。
离线 `gate.sh` 不安装或调用格式工具；本地提交前应另跑格式检查。
GitHub 分支保护是否将该检查设为必需项由仓库设置决定，工作流文件不会自动修改该设置。

后续批量调整按模块单独做排版提交，先审查文件范围与已有未提交改动。
格式提交不混入命名、函数拆分或业务修复。`InsertBraces` 会增加 token，
不能把它当作纯空白改动免审；宏、条件编译、测试源码匹配和变异锚点尤其需要检查。
同步受影响脚本的匹配锚点时保留断言与目标红口径，不删保护换绿。
实际改动源码后，依 AGENTS.md 执行核心闸门、对应平台构建和受影响变异验证。
格式检查不替代编译、行为与变异验证。
